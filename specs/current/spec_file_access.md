## Goal
Файловый доступ агента: пять операций (`list`, `search`, `read`, `write`, `edit`), которыми агент навигирует по проекту, читает и изменяет файлы. Плюс bootstrap-дерево, инжектируемое в контекст в начале сессии. Мост между текстовым чатом LLM и реальной файловой системой проекта — через CLI, единственную точку исполнения.

Ключевой принцип: **агент никогда не придумывает путь.** Путь либо обнаружен (`list`/`search`), либо возвращён CLI. Все пути относительны корня проекта; корень — граница безопасности.

## Input
- **Вызов:** тег-блок `[FS | op: ... | ...]` из ответа модели, извлечённый content script'ом (`spec_llm_message_format`) и переданный CLI
- Для `write`/`edit` — тело heredoc сразу после тега, до объявленной в `end:` строки-маркера
- Корень проекта из `freeagent.config.json`

## Output
- **Результат:** JSON-объект в теге `[FS_RESULT]`, инжектируемый обратно в контекст модели (`spec_llm_message_format`)
- Форма результата — success (`ok: true`) или error (`ok: false`) с кодом ошибки

## Contract

### Формат вызова

Вызовы используют тот же `[TAG | pipe]` синтаксис заголовка, что и вся шина. Метаданные операции (`op`, `path`, `query`, `type`, `kind`) — в pipe-теге. Тело файла (только `write`/`edit`) выносится **после** тега как heredoc: тег объявляет строку-ограничитель в поле `end:`, тело читается дословно до строки, в точности равной этому ограничителю.

**Почему heredoc, а не fenced-блок.** Тело `write`/`edit` — это полезная нагрузка, которая сама может содержать тройные бэктики (код с markdown в строках, template literals). Fenced-обёртка (```) в этом случае двусмысленна: парсер не отличит закрывающий забор от бэктиков внутри кода. Heredoc с объявленным маркером снимает это — парсер ищет не бэктики, а конкретную строку `end:`, а тело между тегом и маркером не интерпретируется вообще (ни бэктики, ни теги, ни `|`). Маркер — фиксированная константа из скилл-промпта (`---FS_END---`), слабая модель копирует её, а не вычисляет; в редком коллизийном случае (сам файл про формат FreeAgent) модель объявляет другой маркер в `end:`.

**Парсер — отдельный, в CLI.** `[FS]`-вызовы разбирает функция `parseFsCall` в CLI, **не** `fromTagFormat` из `/shared/bus-types`. Причина — слоевая: `fromTagFormat` инлайнится в браузерный бандл расширения, а `[FS]` (валидация пути, `FORBIDDEN_PATH`, tail-truncate, доступ к диску) — чисто CLI-логика, которой в расширении быть не должно. Плюс дисциплины тела противоположны: `[MSG]`-тело — JSON (`fromTagFormat` глобально снимает бэктики и делает `JSON.parse`), `[FS]`-тело — дословный текст с сохранёнными бэктиками (heredoc). Слить их в одну функцию значило бы дать две несовместимые ветки и протащить disk-логику в браузер. «Один парсер» из общей философии здесь — про единый синтаксис *заголовка* тега, не про единое тело функции.

**Ровно один вызов на ход.** Всё после первого закрытого вызова (строки-маркера `end:`) обрезается (см. Constraints, tail truncation).

### Пять операций

**`list` — дерево директории.**
```
[FS | op: list | path: src | depth: 2]
```
- `path` — директория относительно корня; `.` для самого корня
- `depth` — опционально, по умолчанию 1; сколько уровней раскрыть

Игнорирует мусор по умолчанию: `.git`, `node_modules`, `dist`, `build`, плюс записи из `.gitignore` и `.freeagentignore` (`spec_context_privacy_filter`). Это **не опция** — иначе дерево заливает контекст тысячами нерелевантных путей.

Success `data`:
```json
{
  "path": "src",
  "tree": {
    "bus": ["router.ts", "message.ts", "types.ts"],
    "supervisor": ["index.ts", "state.ts"],
    "orchestrator": ["index.ts"]
  }
}
```
Директория → объект (её дети); файл на листе запрошенной глубины → элемент массива. Директория глубже `depth` → ключ с пустым объектом (сигнал «внутри есть, не раскрыто»).

**`search` — поиск по содержимому или имени.**
```
[FS | op: search | query: class MessageBus | type: content | path: src]
```
- `query` — строка поиска
- `type` — `content` (ripgrep по телам файлов) или `name` (glob по именам/путям)
- `path` — опционально, область поиска; по умолчанию корень

Success `data` для `content`:
```json
{
  "results": [
    {
      "path": "src/bus/router.ts",
      "matches": [ { "line": 12, "text": "export class MessageBus {" } ],
      "reason": "content match: 'class MessageBus' (1 occurrence)"
    }
  ]
}
```
Success `data` для `name`:
```json
{
  "results": [ { "path": "src/bus/router.ts", "reason": "name match: 'router'" } ]
}
```
`reason` объясняет модели, почему файл всплыл — это существенно помогает выбрать нужный кандидат, когда имена похожи. Пустой результат — это success, не error: `{ "results": [] }`.

**`read` — чтение файла.**
```
[FS | op: read | path: src/bus/router.ts]
```
Success `data`:
```json
{ "path": "src/bus/router.ts", "content": "export class MessageBus {\n  ...\n}\n" }
```
Файл больше byte-cap контекста → `FILE_TOO_LARGE` (не молча обрезанный content — иначе модель примет усечённое за полное). Точное значение cap калибруется на реальных прогонах (см. Open items), но код ошибки и сам факт проверки — часть контракта уже в PR-4.

**`write` — создать или перезаписать файл.** Тело — heredoc после тега, до строки-маркера `end:`.
```
[FS | op: write | path: src/bus/message.ts | kind: code | end: ---FS_END---]
export interface Message {
  from: string;
  to: string;
}
---FS_END---
```
`kind` — тип содержимого: `code` | `test` | `doc` | `data`. В PR-4 поле **записывается, но не enforced** (как в yolo — пишет кто угодно что угодно). Оно закладывает шов: `spec_write_path_validation` (PR-7) и `spec_plan_execution` (PR-8) используют `kind` для владения файлами по плану (тестер эмитит `kind: test`, кодер — `kind: code`; чужой `kind` в чужой файл ловится уровнем-3 валидации). Дефолт при отсутствии — `code`. Заложить поле сейчас, чтобы PR-7/8 не ретрофитили формат тега задним числом.

Success `data`:
```json
{ "path": "src/bus/message.ts", "bytes_written": 61, "created": true, "kind": "code" }
```
`created` — `true` для нового файла, `false` для перезаписи, чтобы модель знала, заменила ли существующее содержимое. `kind` эхом возвращается — подтверждение, что CLI распарсил поле.

**`edit` — заменить точную строку в файле.** Тело — один heredoc, внутри разделённый фиксированными маркерами `---OLD---` и `---NEW---`: сначала старый фрагмент, затем новый. `old` обязан встречаться в файле **ровно один раз** — это заставляет модель включить достаточно контекста для уникального совпадения (аналог str_replace). Внутренние маркеры `---OLD---`/`---NEW---` — тоже фиксированные константы; парсер режет тело на две части по ним. Никаких вложенных заборов, никакого счёта бэктиков — как и у `write`, тело между маркерами дословно.
```
[FS | op: edit | path: src/bus/router.ts | end: ---FS_END---]
---OLD---
  private handlers = [];
---NEW---
  private handlers: Handler[] = [];
---FS_END---
```
Success `data`:
```json
{ "path": "src/bus/router.ts", "replaced": true }
```
Если `old` совпадает ноль раз или больше одного — это **ошибка** (`NOT_FOUND` либо `AMBIGUOUS_MATCH`), **никогда не тихий no-op**. Молчаливая правка не в том месте для PR-bounded работы — катастрофа.

### Формат результата

Каждый исполненный вызов возвращает `[FS_RESULT]` c JSON ровно одной из двух форм.

Success:
```
[FS_RESULT]
{ "ok": true, "data": { ... } }
[/FS_RESULT]
```
Error:
```
[FS_RESULT]
{ "ok": false, "error": { "code": "ERROR_CODE", "message": "...", "hint": "..." } }
[/FS_RESULT]
```
Булев `ok` даёт и модели, и коду ветвиться без двусмысленности. `error.code` — стабильный machine-readable enum; `message` читает модель; `hint` — опциональная подсказка, направляющая восстановление. Структурный объект ошибки оставляет простор добавить поля в будущем, не ломая парсеры.

### Коды ошибок

| code            | значение                                             | типичный hint                                   |
|-----------------|------------------------------------------------------|-------------------------------------------------|
| UNKNOWN_OP      | `op` не одна из пяти операций                         | перечислить пять валидных операций              |
| PATH_ESCAPE     | абсолютный путь или `../` — вне корня проекта         | использовать путь относительно корня            |
| FORBIDDEN_PATH  | путь валиден и внутри корня, но защищён от записи (`.git/`, `.env`, и в PR-7 — не-твой-по-плану файл) | не трогать служебные пути; писать только в файлы задачи |
| NOT_FOUND       | путь (или `old`-строка `edit`) не существует          | использовать `list`/`search`, чтобы найти цель  |
| AMBIGUOUS_MATCH | `old`-строка `edit` совпадает больше одного раза      | добавить окружающий контекст для уникальности   |
| BAD_ARGS        | отсутствует/некорректен обязательный аргумент         | повторить обязательные аргументы                |
| MULTIPLE_CALLS  | больше одного вызова в одном ходу                     | один вызов за ход, затем ждать                  |
| FILE_TOO_LARGE  | `read`: файл превышает byte-cap контекста             | читать частями или сузить через `search`        |
| IO_ERROR        | сбой файловой системы (права и т.п.)                  | (пробрасывается как есть)                        |

> Коды — enum намеренно: CLI ветвится по ним, новые коды добавляются, не трогая существующую обработку. `UNKNOWN_OP` заменяет `UNKNOWN_TOOL` из исходного контракта, потому что в `[FS]`-формате операция задаётся полем `op`, а не именем тула.

### Enforcement на стороне CLI

Enforcement живёт в CLI, а не в доброй воле модели. Каждый вызов валидируется **до** исполнения. Это реальный слой контроля — системный промпт просит модель вести себя правильно, этот код это гарантирует. Каждая проверка соответствует правилу промпта роли.

Перед исполнением, по порядку:
1. **Один вызов.** Если в ходу больше одного `[FS]`-вызова — исполнить первый, вернуть `MULTIPLE_CALLS` для остальных. Обрезать прозу, написанную моделью после первого закрытого вызова.
2. **Известная операция.** `op` не одна из пяти → `UNKNOWN_OP`.
3. **Аргументы на месте.** Нет `query`, `path` и т.п. → `BAD_ARGS`.
4. **Путь не убегает из корня.** Разрезолвить относительно корня (`path.resolve` + `fs.realpath` для симлинков). Абсолютный, содержит `../`, или резолвится вне корня → `PATH_ESCAPE`. Сырой путь от модели никогда не проходит непроверенным.
5. **Путь не защищён** (для `write`/`edit`). Путь резолвится внутри корня, но попадает в защищённую зону (`.git/`, `.env`, `.freeagent/` служебные файлы) → `FORBIDDEN_PATH`. Отличие от `PATH_ESCAPE`: там путь *вне* корня, здесь — валиден и внутри, но писать туда нельзя. В PR-4 это фиксированный список защищённых путей; PR-7 (`write_path_validation`) расширяет уровнем-3 (владение по `PlanStep.files`), возвращая тот же `FORBIDDEN_PATH`.
6. **Цель существует** (для `read`/`edit`/`list` по конкретному пути). Нет → `NOT_FOUND` с подсказкой искать.

Только после всех проверок вызов доходит до файловой системы.

Два поведения — это enforcement, не валидация, и важны не меньше:
- **Tail truncation.** Браузерные модели без нативного tool-use часто продолжают писать после закрытия вызова (претрейн тянет «договорить»). CLI/extension обрезает всё после первого закрытого `[FS]`-вызова, исполняет, возвращает результат, даёт модели продолжить с этой точки. Не полагаться на то, что модель остановится сама; полагаться на то, что система её остановит.
- **Result injection.** Модель никогда не должна видеть результат, который написала сама. Авторитетны только `[FS_RESULT]`-блоки, произведённые CLI.

> **Связь с `write_path_validation` (PR-7).** Проверка пути здесь (уровни 1–2: traversal, защищённые пути) и `spec_write_path_validation` — одна и та же логика в одной точке. `file_access` вводит её для `write`/`edit`; `write_path_validation` (PR-7) расширяет уровнем-3 (владение файлом по `PlanStep.files`). В PR-4 уровень-3 отсутствует (как в yolo). Не дублировать резолвер — заложить общий `validateWritePath(root, path)`, который PR-7 обернёт уровнем-3.

### Bootstrap дерева проекта

В начале сессии, **до первого хода модели**, CLI автоматически инжектирует дерево проекта (`list` от корня, depth 2–3, отфильтрованное как выше) в контекст. Модель начинает работу, уже зная структуру. На практике это плюс `search` покрывает большинство нужд; ручной `list` тогда редок — в основном чтобы раскрыть директорию, свёрнутую на глубине bootstrap.

> **Потребители bootstrap.** На это дерево уже ссылаются `spec_md_orchestrator` (чтобы называть реальные пути в `FILES:` плана) и `spec_cli_plan_mode` (план по реальным путям, не выдуманным). Bootstrap — часть этого PR; оба потребителя замыкаются на него.

## Constraints
- Пять операций — **единственный** способ агента коснуться файлов. Других нет
- Исполнение — **только в CLI** (единственная точка доступа к диску), как `WRITE`-валидация. Content script лишь извлекает `[FS]`-теги и передаёт их; результат инжектирует обратно (`spec_llm_message_format`)
- Синтаксис *заголовка* вызова — тот же `[TAG | pipe]`, что вся шина. Никакого XML. Тело `write`/`edit` — heredoc до объявленного в `end:` маркера, не fenced-блок (бэктики легитимно встречаются в теле кода и ломали бы забор)
- `[FS]`/`[FS_RESULT]` парсит **отдельная `parseFsCall` в CLI**, а не `fromTagFormat` из `/shared/bus-types`. `fromTagFormat` инлайнится в браузерный бандл — disk-логике `[FS]` там не место (протечка слоёв); плюс дисциплины тела несовместимы ([MSG]=JSON со снятием бэктиков, [FS]=дословный heredoc). `parseFsCall` живёт рядом с enforcement и диспетчером в CLI
- Нормализация пути через `path.resolve` + `fs.realpath`, не регулярками — ОС знает свою ФС лучше. На Windows проверка префикса case-insensitive (NTFS)
- `list` обязан фильтровать мусор и privacy-exclude по умолчанию — иначе контекст модели затопляется
- Все пути в результатах — относительно корня. Абсолютный путь корня наружу в контекст LLM не утекает

## Implementation notes

### Системный промпт роли (правила поведения)
Файловый доступ бесполезен без правил, «вытаскивающих» tool-use из браузерной модели. Эти семь правил идут в скилл-файлы агентов (те, что работают с файлами) — не в оркестратора. Каждое закрывает конкретный класс багов; enforcement выше дублирует их в коде (промпт просит, CLI гарантирует).

1. **Один вызов за ход, затем стоп.** Ничего не писать после закрытия вызова. Не эмитить несколько вызовов в одном ходу
2. **Ждать `[FS_RESULT]` перед продолжением.** Никогда не писать результат самому — настоящий результат приходит от системы, не от модели
3. **Чтобы использовать операцию — эмитить вызов, не описывать его прозой.** «Я прочитаю файл» не делает ничего; действует только `[FS | op: ...]`
4. **Никогда не придумывать путь.** Обнаруживать через `list` или `search`. Не уверен, что файл есть — искать
5. **Каждый путь относителен корня проекта.** Никаких абсолютных путей и `../`
6. **Если операция вернула ошибку — исправить подход перед продолжением.** `NOT_FOUND` значит путь неверный → искать правильный
7. **Использовать только пять операций:** `list`, `search`, `read`, `write`, `edit`. Других не существует

> Полный текст скилла с этими правилами и одним few-shot примером вызова — в Приложении A. Формат и правила текстуально просты (их читают слабые модели), как требует `spec_md_orchestrator`.

### Порядок реализации (по вертикалям, каждая проверяема)
Строить от ядра наружу, модель — последней. Каждый шаг заканчивается зелёным прогоном до следующего:
1. Пять функций `fs.*` по одной, path guard первым (`read` + traversal-тест + защищённый путь → `FORBIDDEN_PATH`), затем `list`/`search`/`write`/`edit`. `edit` — последней, с `AMBIGUOUS_MATCH`. Тест — ручной скрипт на реальной ФС
2. Диспетчер: `{op, args}` → результат `[FS_RESULT]` (success/error). Тест — все коды ошибок enum
3. `parseFsCall` (в CLI, отдельно от `fromTagFormat`): текст → `{op, args}` + извлечение heredoc-тела до `end:`-маркера. Тест — case-таблица (чистый вызов; тело с `|`, бэктиками и строкой, похожей на тег, внутри; хвост после маркера; два вызова; `edit` с `---OLD---`/`---NEW---`)
4. Сборка вертикали: текст → парсер → enforcement → диспетчер → `[FS_RESULT]`. Тест — играешь модель руками, end-to-end без LLM
5. Живая браузерная модель + скилл-промпт. Здесь всплывают баги модели/промпта — код уже проверен на шаге 4

## Tests
### Unit
1. `read` валидного пути → content возвращён
2. `read` `../../etc/passwd` → `PATH_ESCAPE`
3. `list` с depth 2 → дерево, `node_modules`/`.git` отфильтрованы
4. `list` директории глубже depth → пустой объект-заглушка
5. `search` content → path + matches (line, text) + reason
6. `search` name → path + reason; пустой результат → `{results: []}` как success
7. `write` нового файла → `created: true`, bytes_written верный, `kind` эхом; тело извлечено из heredoc дословно (с `|`, тройными бэктиками и строкой, похожей на тег `[FS | ...]`, внутри кода — ничего не срезано, парсер нашёл конец по `end:`-маркеру)
8. `write` существующего → `created: false`
9. `write` без `kind` → дефолт `code`; `write` с `kind: test` → эхо `test` (поле принимается, не enforced в PR-4)
10. `write`/`edit` в защищённый путь (`.git/config`, `.env`) → `FORBIDDEN_PATH`, файл не тронут
11. `edit`, `old` уникален → `replaced: true`; тело режется на old/new по `---OLD---`/`---NEW---`
12. `edit`, `old` совпадает 0 раз → `NOT_FOUND`; 2+ раз → `AMBIGUOUS_MATCH` (не no-op)
13. `read` файла больше byte-cap → `FILE_TOO_LARGE` (не усечённый content)
14. Неизвестная `op` → `UNKNOWN_OP`; отсутствует обязательный арг → `BAD_ARGS`
15. Два `[FS]`-вызова в ходу → первый исполнен, `MULTIPLE_CALLS` для второго
16. Проза после закрывающего `end:`-маркера первого вызова → обрезана (tail truncation)
17. Результат имеет форму `{ok, data}` или `{ok, error:{code,message,hint?}}`

### Integration check
Живая LLM получает bootstrap-дерево → задача «найди где определён X» → эмитит `[FS | op: search]` → CLI парсит, исполняет, возвращает `[FS_RESULT]` → модель эмитит `[FS | op: read]` по возвращённому пути → round-trip текст ⇄ `[FS]` ⇄ CLI ⇄ `[FS_RESULT]` ⇄ текст без потери. Проверить на минимум 2 разных LLM.

## Приложение A — Скилл-промпт файлового доступа

Вставляется в скилл-файлы агентов, работающих с файлами. Текстуально простой (читают слабые модели), один few-shot пример.

```markdown
Ты работаешь с файлами проекта через операции. Другого доступа к файлам нет.

## Как вызвать операцию

Эмить ровно такой формат:

[FS | op: ОПЕРАЦИЯ | арг: значение]

Затем ОСТАНОВИСЬ. Результат придёт в блоке [FS_RESULT]. Продолжай только после него.

Пример:
Задача: где определён класс MessageBus?
Ответ: [FS | op: search | query: class MessageBus | type: content]

Для write и edit тело идёт сразу после тега и заканчивается строкой-маркером ---FS_END--- на отдельной строке. Внутри можно писать что угодно, включая тройные бэктики — они не сломают вызов.

[FS | op: write | path: src/message.ts | kind: code | end: ---FS_END---]
export interface Message { from: string; to: string; }
---FS_END---

Для edit тело содержит старый и новый фрагмент, разделённые ---OLD--- и ---NEW---:

[FS | op: edit | path: src/router.ts | end: ---FS_END---]
---OLD---
  private handlers = [];
---NEW---
  private handlers: Handler[] = [];
---FS_END---

## Операции (только эти пять)

- [FS | op: list | path: ПУТЬ | depth: N]        — дерево директории (depth по умолчанию 1)
- [FS | op: search | query: ТЕКСТ | type: content|name | path: ПУТЬ]
- [FS | op: read | path: ПУТЬ]
- [FS | op: write | path: ПУТЬ | kind: code|test|doc|data | end: МАРКЕР]  + тело, затем МАРКЕР на своей строке
- [FS | op: edit | path: ПУТЬ | end: МАРКЕР]   + ---OLD--- старый / ---NEW--- новый / МАРКЕР

## Правила

1. Один вызов за ход, затем стоп. Для write/edit вызов заканчивается строкой ---FS_END---; после неё не пиши ничего. Не эмить несколько вызовов сразу.
2. Жди [FS_RESULT] перед продолжением. Никогда не пиши результат сам.
3. Чтобы использовать операцию — эмить вызов, не описывай его словами.
4. Никогда не придумывай путь. Найди его через list или search. Не уверен что файл есть — ищи.
5. Каждый путь относителен корня проекта. Никаких абсолютных путей и «..».
6. Ошибка в ответе — исправь подход. "not found" значит путь неверный, ищи правильный.
7. Только пять операций выше. Других не существует.
8. Для write/edit всегда закрывай тело строкой ---FS_END--- на отдельной строке. Служебные пути (.git, .env) не трогай.
```
