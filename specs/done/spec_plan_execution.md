# Spec: plan_execution
# Version: 1.0 — НОВАЯ
# Читать вместе с ARCHITECTURE.md (§8 разгрузка оркестратора, §10 параллелизм)

## Goal
Утверждённый план исполняется CLI механически. Оркестратор просыпается только на исключениях. Это главный механизм экономии его контекста.

## Input
`PLAN` от оркестратора после подтверждения пользователем (`spec_cli_plan_mode`)

## Output
- Задачи агентам по порядку зависимостей
- Эскалация оркестратору при отклонении от плана
- `NOTIFY: PLAN_COMPLETE` по завершении

## Contract

### Формат плана
```typescript
interface PlanStep {
  step_id: number;
  agent_id: string;
  description: string;
  files: string[];        // какие файлы шаг трогает — основа контроля владения
  depends_on: number[];   // step_id, после которых можно стартовать
}
```

### Исполнение
```
1. CLI строит граф по depends_on
2. Шаги без незакрытых зависимостей → готовы к запуску
3. Проверка пересечения files среди готовых:
     пересекаются → исполнять последовательно
     не пересекаются → параллельно
4. Отправка TASK, ожидание RESULT
5. RESULT: DONE → верификация (spec_verification)
     тесты зелёные → шаг закрыт, разблокируются зависимые
     тесты красные → эскалация
6. Все шаги закрыты → NOTIFY: PLAN_COMPLETE оркестратору
```

### Когда будим оркестратора
Только при: `RESULT: FAILED`, красных тестах, `WRITE` вне заявленных `files`, агент `FAILED` после всех попыток, самооценка ниже порога, план исчерпан.

**На счастливом пути оркестратор не получает ни одного сообщения** до `PLAN_COMPLETE`.

### Дедупликация статусов
`STATUS` с неизменившимся состоянием оркестратору не пересылается. Изменение состояния — одна строка.

## Constraints
- **`WRITE` на файл вне `files` своего шага отклоняется** с `ERROR` (ARCHITECTURE §10)
- Валидация плана до старта: все `agent_id` существуют, нет циклов в `depends_on`, нет ссылок на несуществующие `step_id`. Невалидный план → возврат оркестратору с описанием проблемы, не выполнять частично
- Задача агенту в переходном статусе (`SWITCHING`, `INITIALIZING`, …) — в очередь, доставка после `READY`; остальные ветки плана продолжаются
- Пользователь может прервать исполнение (`/stop`) — текущие задачи дорабатывают, новые не отправляются
- План строит слабая модель и он будет местами неверным — **путь эскалации обязателен и должен быть надёжным**

## Dependencies
`spec_cli_plan_mode`, `spec_verification`, `spec_message_bus_types`, `spec_cli`

## Tests
### Unit
1. Линейный план из 3 шагов исполняется по порядку без участия оркестратора
2. Два независимых шага с непересекающимися files → параллельно
3. Два шага с пересекающимися files → последовательно, несмотря на отсутствие depends_on
4. Цикл в depends_on → план отклонён до старта, ничего не выполнено
5. Несуществующий agent_id в плане → отклонён с указанием валидных
6. `WRITE` вне заявленных files → `ERROR`, файл не записан
7. Красные тесты → эскалация оркестратору с текстом ошибки, зависимые шаги не стартуют
8. Дедупликация: 20 одинаковых STATUS → оркестратору 0 сообщений
9. Задача агенту в `SWITCHING` → очередь, доставка после `READY`, остальные ветки идут

### Integration check
Реальный план на 4 шага с двумя параллельными ветками → полное исполнение → оркестратор получил только `PLAN_COMPLETE`

### Definition of done
- Тесты зелёные
- На счастливом пути число сообщений оркестратору = 1
- Прогон integration check'ов предыдущих PR
